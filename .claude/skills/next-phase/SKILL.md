description: Resume the build at the next unticked phase in docs/PLAN.md

This is the working loop. It lives here and nowhere else. It has two modes, set by the `mode:` line in `docs/STANDING.md`: `gated` (the owner merges every phase) and `run-through` (the run merges its own phases and stops only where the owner is needed). No file, or any other value, means gated. Steps are the same in both unless a step says otherwise.

1. **Where things stand.** Read CLAUDE.md, docs/STANDING.md and docs/PLAN.md. Everything needed to resume is in the repository: a fresh session, on any machine, starts here.
   - Look for work already under way before starting any: `git ls-remote --heads origin 'phase-*'` and `gh api 'repos/<owner>/<repo>/pulls?state=open'`. The newest phase branch carries the newest docs/PLAN.md; check it out and read the plan there, not only on the default branch.
   - If "Waiting on you" in docs/PLAN.md is not "Nothing.", or `bash .claude/hooks/stop.sh list` shows an open issue, the build is stopped. Read the answers: `stop.sh answers <n>` prints comments from the owner's login and drops everyone else's and the build's own notes; an answer may also be in this session. Where the stop was for the owner to merge a pull request (a checkpoint, Phase 0, a phase the gate left for them), the merge is the answer: check the pull request's state. If everything asked is answered, and the answer was the owner's merge of the pull request: that branch is finished, and nothing committed to it reaches the default branch. Update the default branch and make the next phase's branch first, and only there close the stop, write the log lines and commit, so git can change branch and the lines are kept. Otherwise, where you stand: move the block and the answers into the phase log, set "Waiting on you" back to the one line "Nothing.", `stop.sh close <n>` (it logs the stop as closed; a stop that had no issue is logged with `run-log.sh stop-closed "no issue; answered in the session"`), commit the plan and the run log, and go on. If not, say what is still open and stop.
   - Do any `undo` the owner wrote in docs/DECISIONS_TO_REVIEW.md before new work.
   - Merges the log does not know about: for every phase whose pull request is merged and that has no `gate-merged` or `merged` line in docs/RUN_LOG.md (the owner merged it, or the session that merged it ended first), write one. Do it on the branch you will commit to next, so update the default branch and make the next phase's branch first: a line written on a branch that is already merged stops git changing branch and never reaches the default branch. There, `bash .claude/hooks/run-log.sh flush` shows whether the gate's own line was only waiting; if there is still none: `bash .claude/hooks/run-log.sh merged "pr=#<n> merged by <login> at <merged_at>" <phase>`. The log is how the retro counts, so it has to be whole.
   - Find the first phase with unticked boxes. Do not start it if the previous gate is unticked or the previous pull request is not merged. Summarise: last log entry, failing tests, open reviewer findings.
   - Run-through, first phase of a session: `bash .claude/hooks/preflight.sh`. Every MISSING line is a stop (step 10), asked together.
2. **Read before planning.** The SPEC and ARCHITECTURE sections the phase touches, and any file in docs/profiles/. Check current docs or installed source for every library the phase uses.
3. **Propose** the step list for the phase and the risks you see. Say in it, with the reason, whether this phase needs the `verifier` (is there anything to run?) and the `challenger` (will it produce eval results, or touch the claim or how it is measured?). The reviewer checks those two statements against the diff.
   - Gated: wait for approval.
   - Run-through: write the step list and the risks at the top of the phase log, then go on. Look ahead for anything in the phase that is on the stop list (step 10) and raise it now, before the work that depends on it, so the owner is asked once and early.
4. **Build** on a branch named `phase-<number>-<words>`. Set the phase to `building` in the Status table and write `bash .claude/hooks/run-log.sh phase-started "<the phase's name>"`. Tests first for core logic, then implement. Run `make check` and fix until it exits 0. `make check` never judges a score: where the project has evals (docs/profiles/llm-app.md), it tests the eval code and runs its plumbing on fixtures, and `make eval` produces the scores. Where the project has `make eval`, run it now, in every phase, once the code is done and before the review: commit the results file it wrote and paste its whole output into the phase log. It has to be in the commit the reviewer, the verifier and the challenger check, because a results file committed after them makes all three stale. After a scripted edit, read its result before the next step; a commit is its own command, never chained after an edit.
   - The run log. `docs/RUN_LOG.md` is the run's record of itself, one line per event. The merge gate and `stop.sh` write their own lines; you write the rest with `bash .claude/hooks/run-log.sh <event> "<detail>"`: `phase-started`, `review`, `verify`, `challenge` (each with the verdict and the commit, every time the agent is run, not only the last), `checkpoint`, `merged`, `stop-closed` (only for a stop that had no issue). Never edit the file by hand. Every call also moves the lines the scripts left waiting into the file, so run `bash .claude/hooks/run-log.sh flush` before each commit of docs/PLAN.md and commit the two files together: a line that is not committed and pushed is lost to a fresh clone. A log line never makes a verdict stale. The gate does read the file: it must be the default branch's copy with whole log lines added, which is what these scripts produce and what a hand edit breaks.
   - Run-through: where you would have asked the owner something that is not on the stop list, decide, and add an entry to docs/DECISIONS_TO_REVIEW.md with the reason and exactly how to undo it. Update the count in the Status block.
   - A paid step: add the most it could cost to the "Spend:" line first. If that would pass the cap in docs/STANDING.md, it is a stop. Under the cap, in run-through, a paid step the plan lists runs without asking; in gated mode it asks, as always.
   - A change to a guard (settings, hooks, agents, this skill, the pre-commit hook, CI): gated mode asks at the edit. Run-through does not ask at the edit; make only a change that does not weaken a check, list it in the log, and know that the merge gate will leave this phase for the owner to merge. The same holds, with no question at the edit in either mode, for `CLAUDE.md`, `docs/SPEC.md`, anything listed in `.claude/hooks/measure-paths.txt`, and any gate, checklist item or phase heading already in docs/PLAN.md: the run may tick boxes and add lines to the plan, and a phase that changes more is the owner's to merge.
5. **Review.** Write this phase's entries in docs/DECISIONS_TO_REVIEW.md first (the reviewer reads them, and a later change to that file makes the review stale). Commit, then run the `reviewer` agent on the phase diff (`git diff <default branch>...HEAD`). Give it the range and nothing about your reasoning. Fix every blocking finding and run it again on the fixed code. Paste its findings into the phase log as it reported them, then what you did about each. Log each run: `run-log.sh review "<its verdict> @ <commit>"`.
6. **Verify.** Run the `verifier` agent once there is something to run, after the reviewer has finished: never both in the same folder at once. A phase with nothing to run (docs only) says so in step 3 and writes `not needed`. Paste its table into the phase log, and log the run: `run-log.sh verify "<pass or fail> @ <commit>"`. If the phase's product is a screen, take screenshots of every state and look at them yourself before handing over.
7. **Challenge.** If the phase produced eval results, or touched the claim or how it is measured (an eval, a threshold, a judge, a label, the claim's wording anywhere), run the `challenger` agent. Where a gate has a measured bar, the eval output is already in the phase log from step 4 (if the gate names the paid run, that command's output, run under the spend rule and committed before the review like the free one): the challenger reads that output against the bars, and whether a bar is met is its reading, not yours. If the eval has to be run again after a fix, the reviewer and the verifier run again on that commit too. Paste its reading of the bars and its three answers into the phase log in its own words, and log the run: `run-log.sh challenge "<its verdict> @ <commit>"`. If it says `change needed`, that is a stop (step 10) in both modes: bring its list to the owner with your recommendation. Do not make the change first and do not argue it down in the log. Whatever the owner decides, the owner merges that phase: the verdict line stays as the challenger gave it.
8. **Evidence.** Write the gate evidence into the phase log: the commands run and their real output. For a measured bar the evidence is the eval output from step 4. Only then tick the gate, and set the phase to `in review` in the Status table in the same commit. A bar that is missed is not ticked, and nothing is loosened to tick it: `make check` is still green, so the results file and the log are committed as they are, for the owner to read; CI's `eval` job is red on the pull request, which is the truth; stop (step 10). A missed bar is a gate that cannot pass, not a red commit. End the log with the three verdict lines, each at the left margin with nothing after the commit, naming the commit that check ran on (if anything but docs/PLAN.md, docs/HARNESS_NOTES.md or docs/RUN_LOG.md changed after a check, run that check again):
   ```
   reviewer-verdict: no blocking findings @ <commit>
   verifier-verdict: pass @ <commit>
   challenger-verdict: no change @ <commit>
   ```
   Write `not needed @ <commit>` for the verifier or the challenger only where step 3 said so (the commit is the one the reviewer checked). Write what the agent said, not what you hoped: a verdict you cannot write truthfully is a finding to fix or a stop.
9. **Hand over or merge.** `run-log.sh flush`, commit (the plan and the run log together), push, open one pull request for the phase with `gh api repos/<owner>/<repo>/pulls -f title=... -f head=<branch> -f base=<default branch> -F body=@<file>` (REST, so it works in a cloud session too). The description is the plan summary plus a link to the phase log. Say how to try it in two minutes and what is not built yet. Keep the body file outside the repository.
   - Gated: stop here, with your message as the hand-over; no issue is opened for an ordinary end of phase. The human reads the evidence and merges.
   - Run-through: `bash .claude/hooks/merge-gate.sh <number>`. It is the only way you merge.
     - Exit 0: merged. The gate's `gate-merged` line is waiting, not committed: it goes into the next phase's first commit, so make that commit and push it before anything else can end the session. Do not call `run-log.sh` between the merge and the new branch: lines moved into the file and not committed stop git changing branch. Update the default branch locally, check the deploy if a merge deploys (a gate worded "after merge" is checked now, with a real browser if there is a screen), set the phase to `merged` or `merged, checked live` in the Status table on the next phase's branch, and start again at step 1 for the next phase without waiting. After the last phase there is no next branch: say in your final message that the build is complete, that the last row reads `in review`, and that the last `gate-merged` line is not in the committed log (step 1 of any later session writes it as `merged`).
     - Exit 3: CI is still running. Wait and run it again. If CI has not reported after thirty minutes, treat it as a stop.
     - Exit 2, 4 or 5: not merged, and its message says why (a checkpoint, a default branch without protection, a guard or measure file in the diff, a stale verdict, red CI, GitHub refusing the merge). The gate has logged the refusal; the line is committed with your next commit of the plan. A default branch that is not protected is the owner's to switch on: it is a stop, with the gate's own words in the block. Fix what is yours to fix (a stale verdict, a red build) and run it again. Otherwise it is a stop (step 10): the pull request stays open for the owner, and their merge is the answer. Never merge another way, and never change what the gate reads so that it passes.
   - A gate that can only be shown on the deployed site, where a merge is the only way to deploy, is worded "after merge" and checked straight after it. If that check fails, the next phase does not start: fix forward on a new branch, or stop.
10. **Stopping.** This step is for a stop that needs an answer, in either mode; the ordinary end of a gated phase is step 9. These stop the run in run-through mode, and nothing else does: a credential or another step only the owner can do; spend that could pass the cap; anything irreversible or outward-facing that docs/STANDING.md does not list as allowed; a gate that cannot pass after a real attempt; a change to what the project claims or how it is measured; a checkpoint; a phase the merge gate leaves for the owner. In gated mode the same things stop the run, and every phase also ends at its open pull request.
    - Before stopping, finish everything that does not depend on the answer, and collect every question you can foresee for the rest of the phase. The owner is asked once.
    - If the gate cannot pass, or the spec or plan turns out wrong: say what is failing and why, and bring measurements of the options, not only the options. Changing the docs comes first: propose the edit and a decision record, wait for approval, then re-plan the phase. Never weaken the gate instead.
    - A checkpoint: `run-log.sh checkpoint "<which one>, pr=#<n>"` before the block is written.
    - Write the block under "Waiting on you" in docs/PLAN.md, replacing "Nothing." and keeping the end marker below it, in plain language a person who has read no log can answer: what stopped and why; each question numbered, with the options, what each costs and your recommendation; what you will do once answered. Set the phase to `waiting on you`. `run-log.sh flush`, commit the plan and the run log, and push.
    - `bash .claude/hooks/stop.sh open "<what is needed, in a few words>"` opens a GitHub issue assigned to the owner with that block, and sounds the notifier on a Mac. It refuses if the plan is not pushed or a stop is already open. If it reports that GitHub refused, the pushed plan is the record: say so. If it opened the issue without its label, write the issue number into the block. It logs the stop as opened, as a waiting line: straight after it, `run-log.sh flush`, commit docs/RUN_LOG.md alone and push, so a fresh clone knows when the wait began.
    - If the PushNotification tool is available, send one: the project, and what is needed, in one line.
    - End your message with the same block, then wait. Do not keep working on anything the answer could change.
11. If the harness got in the way or lacked something, add a line to docs/HARNESS_NOTES.md.
