# 0010: forty cases in two sets, a rules-only baseline, tighter definitions

**Status:** accepted by the owner, 2026-11-19 (answers to the Phase 0 stop, issue #2). Changes [0008](0008-evals.md) in part.

**Context.** The first measure was twenty cases labelled from the rubric's bands. At the end of Phase 0 the challenger, and before it a reviewer, each wrote about 130 lines of if/else from `evals/RUBRIC.md` that reproduced every label. A rules engine with no model would have scored full marks, so passing the bars would have shown that the model follows a table, not that it makes the "judgment-call" the claim names. The challenger also found that the bars were coarse (27 expected items, four risk types expected once), that "harmful" missed the sixth to eighth risks a handled click brings into view, that output dropped by validation had no defined score, and that nothing stopped a prompt being re-run until it passed.

**Decision.** The owner chose to keep the claim's wording and make the measure able to show it.

- **Two sets.** Thirty table cases, whose labels are the bands and are re-derived by a test, and ten open cases, where the bands do not settle the matter and the label is a written call with its reason. Every risk type is expected in at least two cases.
- **Who writes the open cases.** The owner will not hand-label. An agent with fresh context that never writes, sees or tunes the prompt drafts them, each with a short reason grounded in public deliverability guidance where it applies (the bulk-sender requirements published by Google and by Yahoo, M3AAWG's sender best practices, the SPF, DKIM and DMARC RFCs). The owner reviews them at the Phase 0 merge. The README says where the labels came from: drafted by AI against written guidance and reviewed by the engineer who built the original system, not by a deliverability specialist.
- **Held out.** Whoever writes or changes a prompt does not read the open cases, their summary in the Phase 0 pull request, or their per-case results. Only their totals are reported. The session that built Phase 0 never opened the case files and checked them by test only, but it did see the drafting agent's one-line summary of each case while putting it into the pull request description. So in Phase 2 the prompt is written and changed by an agent with fresh context that is given the rubric and the table cases and nothing else; the building session passes it table-case results only.
- **A rules-only baseline.** The bands applied by code (`backend/src/domain_health/evals/table.py`) are scored with the same harness and reported beside the model, for the table set and the open set. On the open set the model does better than the baseline when it finds on average at least one more expected item per run than the baseline, its harmful count is no higher, and its precision is at least 0.80. (The baseline's precision there is 1.00 by construction, which a test keeps true, so precision is held to its bar, not to the baseline. As the cases stand, the baseline finds 9 of the 14 expected items on the open set, with nothing harmful, so the model needs at least 30 of 42 over three runs.) If it does not, the build stops for the owner and proposes the weaker wording: "judgment-call risks picked by a model from a closed list and scored against a written rubric".
- **Definitions.** Harmful counts everything returned, up to eight. Dropped output found nothing for coverage, never matches for stability, and is counted beside the measures. Stability is a share, at least 0.90. Coverage is also reported per risk type. "Harmful 0" is written as "0 in 120 case-runs". Precision is kept although it adds little on the table cases.
- **Rules for paid runs.** The gate's numbers are one run of the final prompt version; every attempt is reported; an unchanged prompt is never re-run to pass; a prompt does not quote the rubric's thresholds.
- **Checks in code.** Table labels and fix lists re-derived from the rubric; an open label must depart from the bands; validators refuse an input that cannot happen; in Phase 2 a test that only a case's `input` reaches the model; in Phase 4 a test that no recording for a seeded client names a type the bands call wrong.

**Consequence.** The bars are still judged on all forty cases, where thirty can be passed by following a table. What shows judgment is ten cases, which is a small number: one open case is a tenth of that evidence, and the comparison with the baseline can turn on one or two calls. The open labels are AI-drafted calls, signed off by the owner, on what a specialist would say; a specialist might disagree with some. `table.py` now exists in the source tree and could be misused as a filter or as prompt material; it is listed as part of the measure and its docstring says what it may be used for. A paid eval run is 120 calls, twice the intake's estimate: about $0.06 on `gpt-6-luna` and about $0.70 on `gpt-6.1-terra`, counted in the plan at $0.10 and $1.00. The worst case for the whole build rises from under $3.50 to under $6, still below the $10 cap; the estimate table in `docs/STANDING.md` is the owner's and still shows the old figures. Revisit if the open set proves too small to separate the model from the baseline, or if a specialist reviews the labels.
